Hard-reality conclusion
The code path the demonstration follows has been executed end to end by a script that clicks the French interface: 41 steps, 40 passed on the sixth run, and the one failure (a webhook subscription created before the fix) was corrected and re-proven through the API. Until those four are done and written down, the platform is a demonstrable product, not a launched one.

SECTION 5Architecture and dependency findings

Architecture summary

One Node/Express 5 API in TypeScript on a single SQLite file (better-sqlite3, WAL, 43 migrations applied at boot), serving the partner API, the console API, server-rendered site and Lite pages. Two static React/Vite front ends (web for customers and acceptors, console for administrators) and an Expo mobile app share @bitripay/shared. Production is three containers plus Caddy on one Hostinger VPS, pulled by a systemd timer every five minutes when GitHub CI is green for the branch head.

Critical dependencies

  • SQLite on a Docker volume: the only datastore, the only ledger. No replica.
  • Caddy: TLS, HSTS, routing. Certificates from Let's Encrypt.
  • GitHub Actions: gate for every deploy (the timer refuses a red head).
  • Official sanctions feeds (OFAC ×2, OFSI, UN, EU): fetched daily by the API. From CI and from this audit environment every fetch returned HTTP 403 (proxy); docs/VERIFICATION.md records a successful fetch from the VPS. Screening degrades to the last imported version, never to "no screening".
  • Anthropic API for the assistant and content agent only; every payment path works without it.

Single points of failure

  • The VPS itself (API, database, proxy, backups on the same host).
  • The one administrator account (B-04).
  • The in-memory rate limiter and dispatcher lease: correct for one instance, not for two (documented in middleware/rateLimit.ts).

Undocumented components

  • None found that carry money. The demo-account script wrote its database at the repository root when run from there; fixed this audit (D-09).

Infrastructure risks

  • Backups live on the same disk as the database (volume backups); no off-host copy.
  • PWA bundles cache: each device needs a hard reload after a deploy (seen twice by the founder).

SECTION 12Observability and incident-response findings

Can be detected and diagnosed today

  • Every request carries a correlation id (X-Correlation-Id in and out) and the API error envelope carries a BP code.
  • Audit log with actor, action, reason (suspension reason proven in the walkthrough); hash-chained event log with integrity endpoint; regulatory export with manifest.
  • Guardian invariants on demand and on schedule; a breach halts payments and notifies every administrator in-app.
  • Health endpoint, SLO page, incidents register (declare, acknowledge, resolve) in the console.

Cannot be detected today

  • Anything that happens while nobody is logged in to the console: there is no e-mail, SMS or push alert wired to Guardian, health or deploy failure (B-05).
  • A failed deploy: the timer logs to /var/log/bitripay-auto-deploy.log only.
  • Resource exhaustion (disk, memory) on the VPS.

Incident owners: not written down. The only inbox is support@bitripay.com.

There was no /api/auth/logout route (the 2FA exemption list named it, the router never defined it). The apps dropped the token locally; the server honoured it for its 7-day life. Found by adversarial check 20 on 16 Sept 17:39 UTC: logout 404, reuse 200.
Change
Every token carries a session id (JWT jti); POST /api/auth/logout records it in the new revoked_sessions table (migration 043) until the token's own expiry; the middleware refuses a revoked id; web, console and mobile call the route before dropping the token; sign-out-everywhere unchanged; API keys get 400 no_session. Tokens issued before the change carry no id and keep working until they expire.
Tests added
auth_logout.test.ts (2 tests: revoked token 401, other device stays signed in, second sign-out 401, fresh sign-in works, row expiry; sign-out-everywhere still works; API key refused).
Retest
Adversarial re-run against the restarted API: before 200 · logout 200 · reuse 401 invalid_token. Full API suite: 59 files / 372 tests passed after the change (lint 0 errors).

SECTION 17Final launch decision

This release is not approved for public launch.
