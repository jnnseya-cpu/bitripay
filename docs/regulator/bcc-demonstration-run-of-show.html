Scènes

25' – 30'

Scène 1 · Ouverture de compte et connaissance client par paliers

Client · Administrateur
Écranswww.bitripay.com sur le téléphone du client · console admin.bitripay.com → KYC
Clics
  1. Téléphone : Créer un compte → nom, numéro de téléphone congolais, mot de passe.
  2. Le code SMS arrive sur le téléphone montré à la délégation ; saisie du code.
  3. Tableau de bord : palier 1 affiché avec ses limites (50 USD par opération, 200 par mois).
  4. Console : KYC → dossier du client B → pièce et selfie → Approuver palier 2 (PIN administrateur).
  5. Téléphone du client B : notification « KYC approuvé », limites relevées.
Résultat attenduCompte créé en moins d'une minute, code SMS réel, limites de palier affichées et relevées après approbation, notification reçue.

Prouve : KYC par paliers conforme à la grille RDC, limites appliquées par le système, décision tracée au journal d'audit.

30' – 36'

Scène 2 · Entrée de fonds mobile money sans API et paiement marchand par QR

Client · Marchand · Téléphone de collecte
ÉcransTéléphone client → Ajouter de l'argent · téléphone de collecte (application dispositif) · téléphone marchand → Encaisser · console → Mobile money & preuves
Clics
  1. Client : Ajouter de l'argent → Mobile money → Orange Money → 20 000 CDF → la plateforme affiche le numéro de collecte, la référence et les frais (0,70 %).
  2. Client : envoi depuis son compte Orange Money vers le numéro de collecte (ou, en salle sans réseau opérateur, injection du SMS opérateur depuis la console → Simulateur, en l'annonçant).
  3. Téléphone de collecte : SMS reçu, signé et transmis ; console → preuve « réglée », rapprochée par référence.
  4. Client : solde CDF crédité, reçu horodaté.
  5. Marchand : Point de vente → Articles & TVA → deux lignes (article, quantité, prix unitaire) → la TVA à 16 % s'ajoute d'elle-même → QR dynamique du total exact.
  6. Client : Scanner → marchand vérifié, articles, TVA, total, frais → PIN → payé.
  7. Les deux téléphones montrent le reçu détaillé (lignes, sous-total, TVA, numéro fiscal) ; Imprimer le reçu ; console → Transactions : les deux écritures et leurs frais.
Résultat attenduCrédit uniquement après preuve signée rapprochée ; paiement QR instantané du montant exact TVA comprise ; frais affichés avant validation et repris sur le reçu détaillé.

Prouve : intégration mobile money sans dépendance à une API opérateur, acceptation QR multi-usages avec point de vente et TVA, transparence tarifaire, grand livre équilibré.

À dire avant le clic 1 : « Le rechargement du portefeuille est une fonction de la phase 2 (monnaie électronique) ; nous la montrons en sandbox pour que vous voyiez la preuve signée et le rapprochement. En phase agrégateur, le même encaissement est reversé au marchand selon son calendrier de règlement, sans solde client. »

36' – 42'

Scène 3 · Réseau d'agents et sortie de fonds à quatre yeux

Client · Agent · Deux administrateurs
ÉcransTéléphone client → Retirer chez un agent, Déplacer de l'argent · téléphone agent → Caisse · console → Instructions de versement, Console de vérification (deux administrateurs)
Clics
  1. Client : Retirer → chez un agent → 10 000 CDF → code de retrait affiché.
  2. Agent : Caisse → Retrait → saisie du code → PIN → confirmation ; l'agent remet les espèces ; sa commission (0,40 %) apparaît dans son relevé de commissions.
  3. Client : Déplacer de l'argent → vers Mobile money → pays RDC → Orange Money → numéro du bénéficiaire → 3 USD payés en CDF au taux affiché (garanti) → transfert « Financé · change réservé », versement en file.
  4. Console → Corridors, liquidité & versements → Instructions de versement : l'instruction avec le montant exact et les étapes USSD ; le versement part de la SIM préfinancée, puis Régler avec la référence opérateur (proposition, administrateur 1).
  5. Console (administrateur 2) : Console de vérification → Approuver (PIN). Montrer que l'administrateur 1 ne peut pas approuver sa propre proposition ; le transfert passe à « Réglé » et le client est notifié.
  6. Console → Liquidité : flotte de l'agent et du compte de versement mises à jour.
Résultat attenduRetrait espèces confirmé par code, commission inscrite ; versement mobile money exécuté depuis la flotte préfinancée et réglé seulement après confirmation par un second administrateur.

Prouve : agents contrôlés et rémunérés sur transactions réalisées, séparation des fonctions, suivi de liquidité.

À dire avant le clic 1 : « Le réseau d'agents et les sorties de fonds relèvent de la phase 2 ; la scène montre les contrôles (code, quatre yeux, flotte) qui existent déjà. »

42' – 48'

Scène 4 · Interopérabilité par API et paiement via le Switch Monétique National (simulation)

Marchand · Système tiers · Administrateur
Écranswww.bitripay.com → Développeurs · terminal ou outil d'API · récepteur de webhooks · console → Switch (Payments, Aggregation fees) · marchand → Centre du marchand → Mes frais
Clics
  1. Marchand : Développeurs → Créer une clé d'API à périmètre restreint (« payment_intents:write ») → secret affiché une seule fois.
  2. Appel POST /v1/payment_intents avec montant, devise, opérateurs autorisés → réponse avec l'identifiant et l'URL de la page de paiement.
  3. Client : ouvre la page de paiement hébergée, paie depuis son portefeuille (PIN).
  4. Récepteur : webhook payment_intent.succeeded reçu avec signature ; vérification de la signature montrée.
  5. Appel GET /v1/payment_intents/{id} : état « réglé » ; rejouer une livraison depuis le portail.
  6. Annoncer « connexion au switch en SIMULATION, institutions fictives ». Appel POST /v1/payments (clé marchand, montant en CDF, bénéficiaire = participant fictif, account_token du payeur se terminant par tok_ok, clé d'idempotence).
  7. Console → Switch → Payments : le paiement passe REÇU → PRÊT → EN COURS → COMPLÉTÉ ; ouvrir la chronologie : faits PRINCIPAL_REQUESTED, CREDIT_CONFIRMED puis AGGREGATION_FEE, chacun avec sa source et son heure ; montrer « aucune écriture au grand livre » (intention sans transaction) et l'étiquette SIMULATION.
  8. Console → Switch → Aggregation fees : l'entrée « accumulée » (0,80 % du montant) ; marchand → Centre du marchand → Mes frais : la même entrée côté marchand. Expliquer la clôture de période et la facture (payée depuis le portefeuille ou par virement).
  9. Renvoyer le même appel avec le même identifiant de commande : 409, aucun doublon. Optionnel si le temps le permet : un payeur tok_timeout → état INCONNU avec chaîne d'enquête, jamais de réémission.
Résultat attenduIntégration complète en trois appels, événements signés reçus par un système externe, documentation OpenAPI visible ; un paiement national routé par le switch simulé, suivi fait par fait, sans écriture au grand livre, avec le frais d'agrégation accumulé pour le marchand.

Prouve : interopérabilité par API avec plateformes e-commerce, systèmes de facturation et services institutionnels ; rôle d'agrégateur tel que décrit page 12 : BitriPay initie, contrôle, suit et réconcilie, le switch route et règle, le marchand paie un pourcentage convenu, jamais prélevé sur le flux national.

48' – 55'

Scène 5 · Contrôles LCB-FT, intégrité, supervision et intelligence sous contrôle humain

Administrateur · Officier de conformité · Marchand
ÉcransConsole → Risque & conformité · Contrôles · Supervision réglementaire · Agents & centres de commande · marchand → Centre de commande · client → Crédit
Clics
  1. Risque & conformité → Sanctions : sources officielles et nombre d'entrées chargées ; tentative de création d'un bénéficiaire portant un nom listé → opération bloquée, dossier ouvert.
  2. Utilisateurs → client B → Geler le solde CDF (motif « ordonnance ») → le client voit la notification obligatoire ; un transfert est refusé avec le motif.
  3. Contrôles → Guardian : lancer le contrôle → « aucun écart » ; expliquer la mise en pause automatique.
  4. Supervision réglementaire → rapport du jour : volumes, canaux, KYC, LCB-FT, couverture des réserves, intégrité.
  5. Exporter le journal (CSV) → afficher le manifeste : nombre de lignes, empreinte SHA-256, chaîne d'événements intacte ; montrer la ligne d'audit de l'export.
  6. Téléphone client : Relevés → Générer le relevé → PDF ; ouvrir le lien « vérifier » : page publique qui confirme le numéro et l'empreinte du relevé sans révéler le titulaire.
  7. Marchand → Centre de commande : poser une question à l'agent de croissance (« pourquoi mes encaissements ont baissé cette semaine ? ») ; montrer que la réponse cite les outils audités utilisés et qu'une action proposée s'arrête à « préparer », jamais « exécuter ». Console → Agents & centres de commande : mode observation, interrupteur général, journal de chaque exécution.
  8. Téléphone client A → Crédit : score de préparation au crédit, facteur par facteur ; dire « informatif, partagé avec un prêteur seulement à la demande du client ; BitriPay n'octroie aucun crédit ».
Résultat attenduBlocage sanctions démontré, gel effectif et notifié, contrôle d'intégrité vert, rapport temps réel et export normalisé avec manifeste ; agents qui proposent sans exécuter, score de crédit informatif.

Prouve : production de rapports transactionnels en temps réel pour contrôle, conformité et audit ; centralisation normalisée des journaux pour la supervision ; l'intelligence d'exploitation reste une aide à la décision sous contrôle humain et il n'y a aucune activité de crédit (page 7).

Si quelque chose échoue

SymptômeQue faire en séance
Le code SMS n'arrive pasDire que le canal SMS est opéré par un fournisseur tiers ; montrer le code dans la console → Communication → Livraisons (statut de livraison) ; continuer avec le compte préparé.
Le SMS opérateur n'arrive pas sur le téléphone de collecteAnnoncer et injecter le SMS depuis la console → Simulateur ; expliquer que le même rapprochement s'applique.
Une opération est refuséeLire le motif affiché (limite, KYC, sanctions, montant hors bornes) : c'est un contrôle qui fonctionne. Le montrer dans le journal d'audit.
Guardian signale un écartMontrer la pause automatique des mouvements d'argent ; c'est le comportement attendu. Ne pas lever la pause en séance.
Un écran reste blanc après un menuFermer l'application ou l'onglet et rouvrir une fois (la nouvelle version s'installe) ; la version en ligne affiche désormais un message et un bouton Recharger au lieu d'un écran blanc.
La délégation préfère le français à l'écranSélecteur de langue en haut de l'application web → Français : toutes les pages basculent immédiatement.
Le paiement via le switch reste « en cours »Le dispatcher tourne sous bail ; attendre dix secondes, rafraîchir la chronologie. S'il reste en cours, montrer l'outbox (Inbox / outbox) et dire que la plateforme n'a émis qu'une fois et attend ; ne pas relancer le dispatcher en séance.
Le centre de commande répond « vérifications intégrées » sans modèleC'est le mode hors ligne annoncé à l'écran ; la réponse reste fondée sur les données du compte. Dire que le modèle est un fournisseur externe optionnel et que rien ne dépend de lui.
Perte de connexionBasculer sur la 4G ; la version Lite (www.bitripay.com/lite) fonctionne sur connexion lente.

Cinq choses à ne pas dire

  • Que la plateforme est « inviolable » ou « 100 % sécurisée » : dire qu'elle est testée, surveillée et corrigée en continu.
  • Que les fonds sont déjà cantonnés : dire que le mécanisme est en place et sera activé avec le compte de cantonnement de l'agrément.
  • Que les cartes virtuelles sont disponibles : elles sont prévues pour une phase ultérieure, sous réserve d'agréments complémentaires.
  • Que BitriPay détient les fonds, règle les paiements nationaux ou octroie du crédit : nous initions, contrôlons, suivons et réconcilions ; le switch et les institutions règlent ; le score de crédit est informatif.
  • Que « l'intelligence artificielle décide » : les agents d'exploitation observent, expliquent et proposent ; toute action passe par une personne et les approbations à quatre yeux.
